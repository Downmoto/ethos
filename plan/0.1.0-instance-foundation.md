# 0.1.0: Instance foundation

## Delivery

Build a single foreground Linux daemon with a host administration CLI. It can initialise an instance, enforce one owner per home, validate and reload configuration, report health, enter maintenance, shut down within a deadline, and detect an interrupted prior run. It starts with no workspace, agent, network listener, or plugin.

## Repository and dependency contract

The implementation is one Cargo monorepo. Create only the crates needed for 0.1.0:

```text
ethos/
  Cargo.toml                 # workspace members, resolver 3, edition 2024, lints
  Cargo.lock                 # committed for reproducible binary builds
  rust-toolchain.toml        # pin Rust 1.100.0
  .github/workflows/ci.yml  # Linux format, lint, test, and locked build
  crates/
    ethos-core/              # instance paths, config, state, lifecycle, health
      Cargo.toml
      src/{lib,home,config,state,lifecycle,health}.rs
    ethos/                   # the one binary: CLI, daemon, local control protocol
      Cargo.toml
      src/{main,cli,daemon,control}.rs
      tests/                 # Linux process and fault-injection tests
```

`ethos-core` must not depend on the binary. The binary composes core services. Later milestones add `are` (Agent runtime engine), `aae` (Agent automation engine), `model_provider`, and plugin crates to this workspace when their code exists. Keep `Cargo.lock` and the toolchain pin under version control; do not create empty future crates.

| Crate | Direct dependencies needed in 0.1.0 |
|---|---|
| `ethos-core` | `serde` derive, `toml`, `rusqlite` with bundled SQLite, `uuid` v4, `libc` for the effective UID |
| `ethos` | `ethos-core`, `clap` derive, Tokio with runtime/net/signal/sync/time features, `serde_json`, `tracing`, `tracing-subscriber` |

Use `std::fs::File::try_lock` for instance ownership and Tokio Unix sockets for local control. Use explicit SQL migrations; no ORM or database pool is needed for the lifecycle database. `state.sqlite` is touched at init, startup, and shutdown, so its operations can run outside async request handling. Axum and the network API begin in 0.2.0.

## On-disk contract

```text
~/.ethos/                   # 0700; --home may select another directory
  config.toml               # 0600; owner-edited instance configuration
  state.sqlite              # 0600; instance identity and lifecycle state
  instance.lock             # 0600; locked for the whole daemon lifetime
  run/                      # 0700; recreated if absent
    control.sock            # 0600; present only while daemon owns the home
```

Resolve home in this order: `--home`, `ETHOS_HOME`, then `~/.ethos`. Canonicalise an existing home, or canonicalise its existing parent before creating a new home; the lock file is always under that resolved path. Reject a non-directory home, unexpected symlink at a managed file path, files owned by another user, or permissions that expose instance state to other users. Compare ownership with the process's effective UID. `init` creates a valid home without starting the daemon. A second `init` of a valid stopped home makes no content changes. If a daemon owns the home, `init` returns `instance_busy` without changing it. A partial or incompatible home returns a diagnostic without replacing configuration or database content; it may create the lock file needed to serialise init.

Future workspace, plugin, and secret locations must be defined when their features arrive. They are not empty scaffolds in this release. Structured logs go to stderr for the external supervisor; the instance stores no log file in 0.1.0.

## Configuration contract

Initial `config.toml`:

```toml
schema_version = 1

[logging]
level = "info"

[shutdown]
grace_seconds = 30
```

| Value | Source precedence | Validation | Change class |
|---|---|---|---|
| Home path | `--home` > `ETHOS_HOME` > default | absolute resolved directory | immutable for a running daemon |
| `schema_version` | TOML | exactly `1` | immutable until a migration |
| `logging.level` | TOML > default `info` | `off`, `error`, `warn`, `info`, `debug`, `trace` | restart |
| `shutdown.grace_seconds` | TOML > default `30` | integer from 1 to 600 | live reload |

Reject unknown keys, wrong types, unsupported schema versions, and out-of-range values. `ethos config check` validates without changing the daemon. `ethos config show` displays effective values and whether each came from the file or a default. Reload parses and validates the whole candidate, then compares restart and immutable fields. If any such field changed, reject the entire reload with the changed field names. Otherwise atomically replace the active config snapshot and increment its in-memory generation. A failed reload leaves the prior snapshot in use. The first real restart-class field is `logging.level`; a new API bind setting will be added in 0.2.0.

## State and lifecycle contract

Use `PRAGMA user_version = 1` and one migration containing:

```sql
CREATE TABLE instance_state (
    singleton INTEGER PRIMARY KEY CHECK (singleton = 1),
    instance_id TEXT NOT NULL,
    clean_shutdown INTEGER NOT NULL CHECK (clean_shutdown IN (0, 1)),
    run_generation INTEGER NOT NULL CHECK (run_generation >= 0)
);
```

`init` inserts one generated instance ID, `clean_shutdown = 1`, and `run_generation = 0`. Startup verifies schema and database integrity, reads the previous marker, then commits `clean_shutdown = 0` and increments `run_generation` before any mutable service starts. A clean shutdown writes `1` only after every authoritative service has stopped or reached a recorded suspension point. A crash, failed startup, or expired shutdown deadline leaves `0`; the next start runs recovery hooks before reporting readiness. Refuse a newer schema or failed integrity check. Migrations run transactionally and never downgrade.

Use an internal lifecycle contract with a service name, dependencies, criticality, `start`, `recover`, `health`, and `stop(deadline)` operations. Validate the dependency graph before startup. Start in dependency order and stop in reverse order. After an interrupted run, recover each service before starting any service that depends on it; domain work must remain inactive until recovery succeeds and admission opens. If a critical service fails, stop already started services and do not report ready. If an optional service fails and can be isolated, mark it and its dependents unavailable, keep unrelated services running, and report degraded health. A critical dependent of an unavailable service prevents readiness. The state database is a critical bootstrap resource; the local control socket is the first lifecycle service. Fake services exercise other branches in tests.

The coordinator must own one authoritative snapshot of service states and admission. Service hooks return typed success or failure; a failure contains a stable code and service name, with diagnostic text only for human display. The coordinator does not interpret service-specific recovery data. A dependency cannot become ready while its prerequisite is unavailable. A service that cannot prove its state after interruption remains unavailable until its own recovery hook resolves it.

| State | Live | Ready for new work | Meaning |
|---|---:|---:|---|
| starting | yes | no | Ownership acquired; validation, service startup, or recovery in progress |
| ready | yes | yes | Critical services healthy; admission open |
| degraded | yes | yes for unaffected work | Isolated optional failure with machine-readable cause |
| maintenance | yes | no | Host administration available; admission closed |
| stopping | yes | no | New work blocked; shutdown in progress |
| stopped or failed | no | no | No responding owner; last durable state remains inspectable |

Maintenance uses one admission gate that later ARE and AAE entry points must call. Entering maintenance blocks new admissions immediately; already admitted work is allowed to finish or suspend under the normal shutdown contract. Leaving maintenance opens admission only if critical health and recovery checks pass.

Startup order is fixed: resolve and validate home; acquire lock; validate config; open and check SQLite; read the previous clean marker; commit the dirty marker and increment generation; start the local control socket; then start registered services in dependency order, running each service's recovery hook after its start when the prior run was interrupted and before starting its dependents; publish ready or degraded health only after all eligible services have resolved. Admission remains closed throughout startup and recovery. The control socket serves status during this period and rejects state-changing commands until startup resolves. A critical failure stops started services and releases the lock only after cleanup. If the dirty marker was committed, leave it dirty for the next start.

Shutdown order is fixed: capture one deadline from the active configuration, publish stopping and close admission; ask active services to finish or persist suspension within that deadline; stop services in reverse dependency order, including removal of the control socket; commit `clean_shutdown = 1` only if all authoritative work has a known durable outcome; close SQLite; release the instance lock. A pending host `stop` connection remains open after the listener closes so the coordinator can return the final outcome after releasing the lock. If the deadline expires, stop waiting, leave the dirty marker, return `deadline_expired` on that connection when possible, and exit so OS ownership is released. The next start must recover or isolate the unfinished work before readiness.

## Command and local-control contract

| Command | Behaviour |
|---|---|
| `ethos --home PATH init` | Create and validate the home, config, and state database; never start a process. |
| `ethos --home PATH run` | Run in the foreground until signal or host stop; refuse an uninitialised or owned home. |
| `ethos --home PATH status [--json]` | Query live health; when stopped, report stopped and the last clean-shutdown marker. |
| `ethos --home PATH config check` | Parse and validate disk configuration without applying it. |
| `ethos --home PATH config show` | Show the active configuration and value sources when running, disk resolution when stopped. |
| `ethos --home PATH reload` | Apply a valid live change or return the exact restart-required fields. |
| `ethos --home PATH maintenance enter leave` | Close or reopen the admission gate through the daemon. |
| `ethos --home PATH stop` | Request graceful stop and wait on that control connection for the final outcome after ownership release. |

Use one bounded JSON request and response per Unix-socket connection, with protocol version `1`, an operation name, and a structured error code. Cap a request at 64 KiB. Keep this protocol private to the local CLI. Bind `run/control.sock` only after the instance lock is held; remove an old socket only after confirming its type and ownership. Home and `run/` permissions plus socket mode restrict access to the instance owner. No network listener exists in 0.1.0. Host commands cannot be reached through the later ordinary API credential.

The wire shape is `{"v":1,"op":"status"}` and a single response `{"v":1,"ok":true,"data":{...}}` or `{"v":1,"ok":false,"error":{"code":"...","message":"..."}}`. Status data includes `instance_id`, `run_generation`, `config_generation`, lifecycle `state`, `live`, `ready`, `admitting`, and an array of `{service,code}` degraded causes. Stable error codes include `invalid_request`, `invalid_config`, `restart_required`, `instance_busy`, `unavailable`, `critical_failure`, and `deadline_expired`. The CLI prints human-readable status by default and the same data object with `--json`; errors go to stderr. Exit codes are 0 for success, 2 for invalid input/config, 3 for busy or unavailable, and 4 for critical or deadline failure.

`status` never treats a PID file as proof of ownership. If the socket is unreachable, probe the instance lock: free means stopped; held means starting or unresponsive, reported as an error. A stopped-state `status` or `config show` holds that lock while reading disk so a daemon cannot start midway through the read. A host `stop` request receives its response on the already accepted connection after the coordinator has committed or preserved the marker and released the lock; a clean outcome returns success, an unknown outcome returns `critical_failure`, and an expired deadline returns `deadline_expired`. If the connection breaks before that response, the CLI reports `unavailable` rather than inferring success from a free lock. SIGINT and SIGTERM use the same shutdown path as `stop`.

## Implementation sequence

Complete these slices in order. Each slice ends with its stated check before work on the next one begins.

### 1. Cargo monorepo and binary

- [ ] Create the root `Cargo.toml` with `resolver = "3"`, members `crates/ethos` and `crates/ethos-core`, shared edition `2024`, and workspace lints. Pin Rust `1.100.0` in `rust-toolchain.toml`.
- [ ] Create `ethos-core` as a library and `ethos` as the only binary. Put the dependency list from the repository contract in their manifests; disable unused default features where practical and commit the generated `Cargo.lock`.
- [ ] Add `clap` commands and global `--home` parsing in `crates/ethos/src/cli.rs`. `main.rs` maps typed errors to the specified stderr text and exit codes. `ethos --version` reports `0.1.0` and `ethos --help` lists only 0.1 commands.
- [ ] Add Linux CI for the required checks below, enabling the fixture test command once slice 8 adds that feature. Check `cargo build --workspace --locked`, `ethos --help`, and `cargo test --workspace --locked` before proceeding.

### 2. Home resolution and idempotent init

- [ ] Implement `home.rs`: select `--home`, `ETHOS_HOME`, or the default; expand the user's home; resolve a canonical absolute path; record the selected source for diagnostics.
- [ ] Validate file types, owner UID against the effective UID, and permission mode before touching existing state. Create a new home with mode `0700`; create `run/` with mode `0700`. Reject a managed path that is a symlink or has the wrong type.
- [ ] Create `instance.lock` with mode `0600` and hold its exclusive lock during init to prevent two initialisers from racing. Under that lock, generate an instance UUID, write the exact initial `config.toml` through a same-directory temporary file with mode `0600`, sync it, rename it, and sync the parent directory. Implement the version-1 SQLite migration and version check here, and create `state.sqlite` with its singleton row in that migration transaction.
- [ ] On an existing fully valid home, `ethos init` returns success without replacing config, changing the UUID, or resetting state. On partial state, fail with the path and repair action; do not overwrite it.
- [ ] Add tests for source precedence, two different homes, permissions, first init, repeated init, partial init, wrong file type, and unsafe mode. Verify that `init` leaves no daemon or socket running.

### 3. Exclusive ownership

- [ ] Open `instance.lock` without truncating it and call `File::try_lock`. Keep the same file handle alive in the daemon owner object until every service has stopped. Map `WouldBlock` to `instance_busy`; preserve other I/O errors.
- [ ] Acquire ownership before opening `state.sqlite` for mutation, deleting any stale socket, or starting services. A PID may be displayed for diagnostics but never decides whether the home is owned.
- [ ] Test a second process on the same home, two processes on separate homes, and `SIGKILL` followed by a successful new owner. Confirm that the lock file remains present across normal stops.

### 4. Strict configuration and reload validation

- [ ] Implement `config.rs` with Serde `deny_unknown_fields` at every table, explicit value validation, and useful file/field diagnostics. Keep the loaded value and its source together for `config show`.
- [ ] Implement `config check` and `config show` for a stopped instance. Running-instance `show` is completed with the control socket in slice 7 so it reads the active snapshot rather than un-reloaded disk edits.
- [ ] Implement candidate validation and comparison as pure core logic: parse the entire disk file, validate every field, and identify restart-required changes without mutating the active snapshot. The coordinator's atomic publication and live CLI reload are completed in slice 7.
- [ ] Add tests for unknown root/nested keys, wrong types, invalid enum and range, malformed TOML, a valid live candidate, a restart-only change, and a mixed live/restart change. Assert rejected candidates leave the input snapshot unchanged.

### 5. SQLite startup and shutdown state

- [ ] Use the version-1 migration from slice 2 when opening state for a run. Enable foreign keys for future schemas; keep the instance database on local storage.
- [ ] At startup, check schema version and integrity before changing the row. Read `clean_shutdown`, then transactionally set it to `0` and increment `run_generation`. Keep the previous value in memory for recovery decisions.
- [ ] At confirmed shutdown, transactionally set `clean_shutdown` to `1`. Leave it at `0` after a crash, failed start after the dirty commit, unknown service outcome, or deadline expiry.
- [ ] Test missing row, extra row, newer schema, corrupt database, and transaction interruption. The forced-death process test follows in slice 8 with fault injection. Assert no automatic downgrade or silent reinitialisation.

### 6. Service lifecycle, health, and admission

- [ ] Implement `lifecycle.rs` with the service contract above and a registry whose dependency graph is validated before startup. Reject duplicate names, unknown dependencies, and cycles.
- [ ] Implement ordered start, per-service recovery before dependent startup, and reverse stop. A critical failure stops already started services. An isolated optional failure disables its dependents and records a stable `{service, code}` cause; a critical dependent prevents readiness.
- [ ] Implement `health.rs` as the sole owner of lifecycle state, service causes, and the admission gate. Publish one consistent status snapshot to the CLI. Add `enter_maintenance` and `leave_maintenance` transitions with the rules above.
- [ ] Unit-test a graph with several fake services: successful order, reverse stop, optional failure, critical failure, failed recovery, dependency failure, and maintenance while a fake operation is already admitted.

### 7. Protected local administration

- [ ] Implement `control.rs`: after ownership, validate and remove only a stale socket at `run/control.sock`; bind a Tokio Unix listener; set socket mode `0600`; accept one versioned, size-limited JSON request per connection.
- [ ] Dispatch `status`, `config_show`, `reload`, `maintenance_enter`, and `maintenance_leave` to coordinator operations. Reload validates the full candidate with slice-4 logic, rejects any restart-required fields without publishing, or atomically replaces the active snapshot and increments config generation once. Return the response and stable errors specified above. Add `stop` with the shutdown coordinator in slice 8. Do not expose state-changing operations on any network socket.
- [ ] Implement CLI clients for those operations and the stopped-instance status fallback. Running-instance `config show` reads the active snapshot through control. An unreachable socket with a held lock reports unavailable.
- [ ] Test valid and invalid protocol versions, oversized and malformed JSON, stale socket paths, socket permissions, status during startup and maintenance, and independent control sockets for two homes.

### 8. Signals, shutdown, and restart recovery

- [ ] Route SIGINT, SIGTERM, and host `stop` into one shutdown coordinator. Capture the active `grace_seconds` once when shutdown begins, close admission, and apply that one deadline to the whole stop sequence.
- [ ] Add the `stop` control operation and CLI client. Keep the accepted connection open through shutdown for the final outcome after lock release; report `unavailable` if it breaks before a response.
- [ ] Require each service to report completed, durably suspended, or unknown. Commit clean shutdown only when none are unknown; preserve the dirty marker otherwise. Release the lock only after control and storage cleanup.
- [ ] On the next start after a dirty marker, run each recovery hook after that service starts but before starting its dependents or opening admission. Keep an unresolved critical service unready; degrade only when its failure can be isolated.
- [ ] Add an `ethos` crate feature named `test-fixtures`, absent from default and release builds. Feature-gated environment inputs register fake services and trigger process-level faults at: after lock, after dirty commit, after control bind, during recovery, during stop, and before clean commit. Verify the next start and durable marker for each point. Test optional failure and deadline expiry with fake services through the feature-enabled binary.

### 9. Documentation and release

- [ ] Document every command, config field and source, directory path and mode, status field, error code, and the meaning of a dirty restart. Include examples for terminal, systemd supervision, and a container without making systemd mandatory.
- [ ] Run the Linux checks below, including process tests, against a clean build and a populated home. Record the command results in the release note and tag `0.1.0` only after the exit gate passes.

## Required checks

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --locked
cargo test -p ethos --features test-fixtures --locked
cargo build --workspace --release --locked
```

Process tests must launch the compiled binary in separate processes. The feature-enabled binary supplies fake services and fault points for tests; the default release binary contains neither. Tests must show: two independent homes run together; two owners of one home cannot; init is idempotent; invalid config and database state fail closed; reload is atomic; optional failure degrades without unsafe readiness; maintenance blocks new admissions; forced termination leaves a dirty marker; recovery precedes dependent startup and readiness; a clean `stop` returns only after lock release; deadline expiry returns an error and never records clean completion. Record both test commands and results in the release notes. The daemon must run without any agent, workspace, provider, or network listener.
